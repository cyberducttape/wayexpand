# Performance baselines

The checked-in matcher benchmark measures the cost of feeding a trigger one
character at a time through an initialized `ExpansionEngine` containing 100,
1,000, or 10,000 snippets. Configuration parsing and engine construction are
excluded from the timed section.

Run it with:

```sh
cargo bench --locked -p wayexpand-core --bench matcher
```

## Baseline: 2026-10-01

Captured on an AMD Ryzen 7 7735U (16 logical CPUs), Linux x86_64, with
`rustc 1.96.0` and Criterion 0.8.2. This is the benchmark recording
toolchain; the project MSRV is Rust 1.92 (see `Cargo.toml`):

| Snippets | Estimate | 95% interval |
| ---: | ---: | ---: |
| 100 | 2.8081 µs | 2.8062–2.8105 µs |
| 1,000 | 2.8166 µs | 2.8151–2.8180 µs |
| 10,000 | 2.8191 µs | 2.8183–2.8200 µs |

These are machine-specific reference values, not a release performance
guarantee. Compare like-for-like hardware and toolchain when investigating a
regression; Criterion's full reports are written to `target/criterion`.

Measured injector p95 latency:

### Previous amplified construction baseline: 2026-10-04 (one alias)

Same machine and toolchain. The workload builds an `ExpansionEngine` from a
pre-parsed, pre-cloned configuration containing aliases, case propagation,
and decomposable Unicode triggers. At 1,000 snippets it used eight aliases
per snippet; at 5,000 and 10,000 it used one alias per snippet. This is a
historical, less-amplified workload; the current benchmark uses two aliases
at 5,000 and 10,000 snippets. This run used a 2 s warmup and 5 s measurement
with 20 samples:

| Snippets | Estimate | 95% interval |
| ---: | ---: | ---: |
| 1,000 | 38.706 ms | 38.199–39.192 ms |
| 5,000 | 57.176 ms | 56.914–57.472 ms |
| 10,000 | 122.88 ms | 122.36–123.47 ms |

The timed operation is engine construction; TOML parsing and config cloning
are outside the measurement. The full benchmark process peaked at 125,304 KiB
RSS under GNU `time -v`. This includes the benchmark harness and prepared
configuration, so it is process-level evidence rather than isolated matcher
memory. Reproduce the RSS observation by building the benchmark, then running
its executable directly with Criterion's `--bench` flag under `/usr/bin/time
-v`; do not time `cargo bench` if you want to exclude compiler memory.

### Current amplified construction baseline: 2026-10-05 (two aliases)

Same machine and toolchain. The current 10,000-snippet workload has two aliases
per snippet, case propagation enabled, and a decomposable Unicode trigger.
The measured operation excludes TOML parsing and configuration cloning. With
a 1 s warmup and 2 s measurement over 10 samples, matcher construction was
160.66 ms (95% interval 159.24–162.11 ms); `/usr/bin/time -v` reported
114,644 KiB maximum process RSS. This is not directly comparable to the
one-alias 2026-10-04 measurement because the workload is more amplified.

Reproduce the current 10,000-snippet measurement and process RSS with:

```sh
cargo bench --locked -p wayexpand-core --bench matcher --no-run
bench_binary=$(find target/release/deps -maxdepth 1 -type f -perm -111 \
  -name 'matcher-*' -printf '%T@ %p\n' | sort -nr | head -n1 | cut -d' ' -f2-)
/usr/bin/time -v "$bench_binary" --bench matcher_construction_amplified/10000 \
  --sample-size 10 --warm-up-time 1 --measurement-time 2
```

### Recheck: 2026-10-05, commit `1bd5ea9`

On the same host and toolchain, rerunning the 10,000-snippet case produced a
162.72 ms estimate (95% interval 160.64–165.09 ms), with a direct-process
maximum RSS of 135,336 KiB. A controlled run of the same benchmark from
`fe65d4b` in a separate worktree and target directory measured 163.31 ms
(160.92–166.14 ms) and 131,048 KiB RSS. Timing is statistically similar; the
current peak RSS is about 3.3% higher. Earlier rechecks on the current binary
reported 132,592 and 133,636 KiB, while the previous single baseline reported
114,644 KiB. This spread indicates the older RSS figure was not representative;
the controlled comparison does not show a large memory regression. Treat these
as process-level observations, not a memory guarantee. The runs used Linux
7.0.0-34-generic and Rust 1.96.0 on the same host.

### Arena matcher: 2026-10-05

The matcher's two tries changed from a `HashMap<char, Node>` per node to
flat arenas with character-sorted edge runs. Same host, Linux
7.0.0-38-generic, Rust 1.96.0. Criterion compared the change against a
baseline saved from the previous commit in the same session (`cargo bench
... -- --save-baseline before`, then `-- --baseline before`); absolute
timings on this host vary between sessions, so only the relative change is
meaningful:

| Benchmark | Before | After | Change |
| --- | ---: | ---: | ---: |
| `matcher_latency/10000` | 8.94 µs | 8.12 µs | −9.1% |
| `matcher_construction_amplified/1000` | 56.5 ms | 39.4 ms | −30.3% |
| `matcher_construction_amplified/5000` | 114.9 ms | 69.7 ms | −39.3% |
| `matcher_construction_amplified/10000` | 224.9 ms | 152.6 ms | −32.2% |

Isolated matcher heap, counted by a global allocator around `Matcher::new`
only (10,000 snippets; "amplified" adds two aliases, case propagation, and a
decomposable trigger; "unicode" uses CJK, Cyrillic, and accented Latin
triggers with the same amplification):

| Workload | Effective triggers | Heap before | Heap after | Build peak after |
| --- | ---: | ---: | ---: | ---: |
| plain | 10,000 | 28.4 MiB | 1.6 MiB | 8.9 MiB |
| amplified | 80,000 | 77.8 MiB | 3.8 MiB | 26.3 MiB |
| unicode | 90,000 | 101.7 MiB | 5.2 MiB | 37.1 MiB |

The build peak is the temporary insertion structure, released before
`Matcher::new` returns. Reproduce the heap figures with:

```sh
cargo run --locked --release -p wayexpand-core --example matcher_memory
```

## Configuration editing

The GUI keeps in-progress edits in a small draft. On explicit save it clones
the whole configuration and validates the candidate before writing. The
`config_edit` benchmark measures those two costs separately at library sizes
up to the documented 10,000-snippet maximum:

```sh
cargo bench --locked -p wayexpand-core --bench config_edit
```

### Baseline: 2026-10-03

Same machine and toolchain as the matcher baseline above. Each snippet has a
trigger, a one-sentence replacement, a description, and two tags.

| Snippets | Clone | Validate |
| ---: | ---: | ---: |
| 100 | 18.2 µs | 25.9 µs |
| 1,000 | 208.7 µs | 306.1 µs |
| 10,000 | 2.14 ms | 3.32 ms |

At the maximum library size the standalone clone and validation together cost
about 5.5 ms. Draft keystrokes edit only a small `Draft`; they do not clone or
validate the library. The duplicate-trigger hint did scan the library on every
editor frame, so it now queries a prebuilt exact trigger/alias index. Complete
library validation remains required immediately before any save, but runs on
the background save worker instead of the UI thread.

The GUI-specific benchmark measures the per-frame trigger-conflict lookup,
the draft-edit plus live-preview computation, and the complete save path
(config clone, edit, full validation, TOML serialization/comment merge, and
revision-checked atomic write):

```sh
cargo bench --locked -p wayexpand-gui --bench gui_edit
```

## Configuration reload and engine build

The `config_reload` group in `config_edit` measures one secure validated file
read, a validated read followed by a secure exact-source revision check, and
file load plus `ExpansionEngine` construction. It covers 100, 1,000, 5,000,
and 10,000 snippets. The revision-check case models concurrent-edit
protection without parsing the same TOML twice. These core workloads exclude
snapshot publication, daemon filesystem watcher delivery, administrator
policy loading, and standard organization and pack layer discovery; those
need a private desktop/fleet fixture to measure without changing host
configuration.

Run it with:

```sh
cargo bench --locked -p wayexpand-core --bench config_edit \
  -- config_reload
```

Criterion stores reload results alongside the existing clone/validation and
matcher measurements in `target/criterion`. Compare them on the same host and
toolchain; these are local file-system and core construction benchmarks, not
an end-to-end daemon reload latency guarantee.

## Template rendering

The `template_render` benchmark covers built-in variable substitution,
eight-level static snippet inclusion (the supported include-depth limit),
rendering a 1 MiB output (the current output limit), and a 512-byte preview of
that same input. It is a core renderer benchmark; clipboard access, GUI work,
forms, and backend insertion are excluded.

```sh
cargo bench --locked -p wayexpand-core --bench template_render
```

Record the Criterion estimates with the CPU and Rust toolchain. The full
render and bounded-preview cases intentionally measure different output sizes;
the preview processes the same 1 MiB input but stops after producing 512
bytes.

### Baseline: 2026-10-28

AMD Ryzen 7 7735U, Linux 7.0.0-38-generic, `rustc 1.96.0`, Criterion 0.8.2.
The ordinary cases used 30 samples; near-limit cases used 10 samples. Values
are Criterion estimates and 95% confidence intervals:

| Workload | Estimate | 95% interval |
| --- | ---: | ---: |
| Built-in substitutions and local date/time | 5.243 µs | 4.871–5.715 µs |
| Eight-level static include | 521 ns | 495–559 ns |
| Full 1 MiB render | 1.035 ms | 1.034–1.037 ms |
| 512-byte preview from 1 MiB input | 316.88 µs | 313.48–319.76 µs |

This is a single-host baseline, not a p95/p99 event-latency measurement or a
release target. In particular, the preview still scans the large source up to
its first output limit; its result allocation is bounded, but its runtime is
not constant in the preview byte budget alone.

An exploratory before/after run on the AMD Ryzen 7 7735U / Rust 1.96.0 host
measured the 10,000-snippet stable check at 348.30 ms (95% interval
271.37–436.14 ms) when both reads parsed and validated TOML, and 93.89 ms
(88.07–100.65 ms) when the second secure read compared source bytes without
parsing again. The central estimate is 73% lower. This was measured while the
shared 16-thread host was heavily loaded, so the figures are evidence that the
second parse was costly, not a release performance baseline. Re-run on an idle
host before making a latency claim.

### GUI measurements: 2026-10-24

Captured on the same AMD Ryzen 7 7735U / Rust 1.96.0 host. The trigger lookup
is size-independent; short Criterion runs varied between roughly 28 and 55 ns
per lookup across sizes, with the spread dominated by host/sample noise. The
full save pipeline is asynchronous in the application, so its duration is
reported separately from typing responsiveness:

| Snippets | Trigger-conflict lookup | Full save pipeline |
| ---: | ---: | ---: |
| 100 | 28–55 ns | 3.17 ms |
| 1,000 | 29–32 ns | 28.81 ms |
| 5,000 | 28 ns | 169.10 ms |
| 10,000 | 28 ns | 354.60 ms |

These save times include the actual private atomic file replacement but
exclude setup-time loading of the starting revision and TOML document. The
measurements show that large saves take hundreds of milliseconds, but no
whole-library scan runs on each keystroke or GUI frame; save progress remains
asynchronous and the full correctness gate is preserved.

### GUI full-save follow-up: 2026-10-28

Re-ran only `gui_full_save` on the same AMD Ryzen 7 7735U / Rust 1.96.0 host
with 10 samples, a 0.5 s warmup, and a 1 s measurement window. Criterion's
central estimates were:

| Snippets | Full save pipeline |
| ---: | ---: |
| 100 | 3.064 ms |
| 1,000 | 29.844 ms |
| 5,000 | 166.86 ms |
| 10,000 | 358.97 ms |

Compared with the 2026-10-24 estimates, Criterion found the 1,000-snippet
case about 3.6% slower and statistically significant in this short run. The
100-snippet case improved; 5,000 and 10,000 showed no significant change.
This is a follow-up measurement, not evidence of a broad save regression. The
short run and shared-host noise make the isolated 1,000-snippet result worth
monitoring rather than treating it as a release-level performance change.

### Typing preview measurements: 2026-10-25

The `gui_typing_preview_edit` case models one replacement-field character edit
followed by the same draft-to-preview computation the GUI runs on repaint. It
prebuilds the shared snippet library outside the timed loop, so it measures
editing and preview work rather than reloading the library. This excludes egui
layout/painting, window-system event delivery, and physical keyboard latency;
it is a preview-computation measure, not an end-to-end keystroke SLO. Run only
these cases with:

```sh
cargo bench --locked -p wayexpand-gui --bench gui_edit -- \
  gui_typing_preview_edit --sample-size 10 --warm-up-time 1 --measurement-time 2
```

On the same AMD Ryzen 7 7735U / Rust 1.96.0 host, Criterion measured:

| Snippets | Estimate (95% interval) |
| ---: | ---: |
| 100 | 13.073 µs (13.015–13.113 µs) |
| 1,000 | 13.309 µs (13.163–13.412 µs) |
| 5,000 | 13.054 µs (13.002–13.145 µs) |
| 10,000 | 13.093 µs (13.061–13.155 µs) |

The preview computation stayed approximately constant with library size,
consistent with the GUI reusing its prebuilt snippet library and constructing
a one-expansion preview engine. Full saves remain size-dependent and
asynchronous as shown above.

### ASCII normalization fast path: 2026-10-25

`ExpansionEngine` tracks the number of non-ASCII scalars in its bounded input
buffer. When that count is zero, the buffer is necessarily NFC, so matching
skips the Unicode normalization quick-check scan. Non-ASCII input still uses
the existing Unicode-aware quick check and grapheme-normalization path. The
counter is updated as characters are appended, evicted, deleted, restored, or
cleared.

Before and after measurements used Criterion with 10 samples, a 1 s warmup,
and a 2 s measurement on the AMD Ryzen 7 7735U / Rust 1.96.0 host:

| Benchmark | Before | After |
| --- | ---: | ---: |
| 4,096-character ASCII buffer, type and backspace | 6.358 µs | 65.690 ns |
| Short trigger, 100 snippets | 8.096 µs | 7.148 µs |
| Short trigger, 1,000 snippets | 8.035 µs | 4.587 µs |
| Short trigger, 10,000 snippets | 4.911 µs | 4.751 µs |

Criterion reported statistically significant improvements for these cases
with this run's sample settings. A 4,096-character decomposed-accent buffer
measured 69.429 µs after the change; this remains on the Unicode normalization
path and is not a paired before/after comparison. These microbenchmarks are
host-specific and do not measure end-to-end keyboard-to-client latency.
